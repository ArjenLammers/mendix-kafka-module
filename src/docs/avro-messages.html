Avro messages in the Kafka module

Capabilities, limitations and what can be mapped. Kafka module 3.0 (Mendix 11.12, Apache Avro 1.12.2), state of commit bb205eb, 13 November 2026.

How this was verified. Every example below is real output, not expected output: the module's own AvroProcessor was compiled into a small harness and fed 46 cases. Receive examples were written by a standard Avro writer (as a Java or Confluent producer would) and decoded by the module. Send examples were encoded by the module and read back by a standard Avro reader. How Studio Pro types the resulting JSON was checked by creating a JSON structure from a sample. The consumer/producer path (schema ID format, schema cache, failure handling) is covered by the UnitTesting tests Tests.TEST_Avro* against a real broker, including an end-to-end test with import and export mappings (5.8). Statements about import/export mappings beyond that are general Mendix behaviour, not tested per case here.

1. How it works

The module converts between Avro binary and JSON text. A Mendix developer never handles Avro objects: received messages arrive in the on-receive microflow as a JSON string, and messages are sent by passing a JSON string. Import and export mappings do the rest.

Receiving

  1. The consumer reads the message value as bytes (Use AVRO switches the consumer to ByteArrayDeserializer).
  2. The schema ID format decides how the bytes are split: Confluent expects byte 0, a 4-byte schema ID, then the Avro data; None treats the whole value as Avro data (schema ID −1).
  3. The schema is taken from the Get Avro Schema microflow (if set and it returns one), otherwise from the consumer's default schema. The microflow's result is cached per schema ID per consumer thread until the consumers restart.
  4. The data is decoded with that schema and written as JSON. Decimals become plain numbers, and optional strings are unwrapped; everything else stays in Avro's JSON form (details in section 3).
  5. The JSON is passed as the Value (String) parameter of the on-receive microflow. Key and headers are passed as strings, as for non-Avro consumers.
  6. If any step fails (wrong format, schema microflow error, invalid schema, data that does not match the schema), the message goes through the consumer's failure handling: Continue logs and skips it, Retry retries it until it succeeds.

Sending

  1. The microflow builds a JSON string (usually with an export mapping) and calls a send action.
  2. The module fills in schema defaults for fields that are left out, converts decimals and optional strings to Avro's JSON form, and encodes the result with the schema.
  3. If a Confluent schema ID other than 0 is given, byte 0 and the 4-byte ID are put in front of the data.
  4. If the JSON does not fit the schema, the send action fails with an AvroTypeException in the calling microflow; nothing is sent.

General rules when sending (all verified):

  • A field that is left out gets its schema default: {"name":"Ada"} with defaults for country, score and note is written as {"name": "Ada", "country": "NL", "score": 0, "note": null}.
  • A required field without a default that is left out fails: AvroTypeException: Expected int. Got END_OBJECT.
  • Null for a required field fails: AvroTypeException: Expected string. Got VALUE_NULL.
  • A wrong type fails, e.g. "41" for an int: AvroTypeException: Expected int. Got VALUE_STRING. A number too large for an int fails as well.
  • Fields that are not in the schema are dropped silently: {"name":"Ada","nickname":"ada"} is written as {"name": "Ada"}.

4. Limitations

  1. High — no schema evolution; a version mismatch can give wrong data without an error. The module decodes with one schema, as both writer and reader schema. Avro data does not contain field names, so if the producer wrote with a different schema version than the one the consumer resolves, the bytes are read against the wrong layout:
    • A field added in the middle by the producer: the values shift. In the test, {"name":"Ada","email":"ada@example.com","age":41} was received as {"name":"Ada","age":15}: age 15 instead of 41, no error.
    • A field added at the end: silently ignored ({"name":"Ada","age":41}).
    • The consumer's schema is newer than the producer's: fails (EOFException: null).
    With the Confluent format, let the Get Avro Schema microflow return the exact schema for each schema ID (from your registry); then every message is decoded with the schema it was written with. With format None, the producer and consumer schemas must be identical.
    Using one schema for both writing and reading is not a defect in itself: it is exactly right as long as that schema is the one the producer wrote with. The risk is only in choosing it (default schema or microflow) per message.
  2. Medium — optional fields other than strings are wrapped. ["null","int"], optional records, enums, arrays, timestamps and decimals arrive as {"int":41}, {"crm.Address":{…}} etc., and must be sent in that form (a plain value fails). Only ["null","string"] is unwrapped. In an import mapping each wrapper is an extra object level. Unions of several non-null types are always wrapped and have no single mappable shape.
  3. Medium — dates and times are numbers. date, time, timestamp-millis/micros and local-timestamp arrive as numbers (days, milliseconds or microseconds) and must be sent as numbers; an ISO date string fails. Convert them in a microflow. Studio Pro types these elements as Integer.
  4. Medium — decimal precision is not checked; values are rounded silently. A value with more decimals than the scale is rounded half-up (0.125 → 0.13 with scale 2). A value with more digits than the precision is written anyway (123456.78 with precision 4), which strict readers may reject. Decimals do arrive and can be sent with full precision (also as a JSON string for very large values).
  5. Medium — bytes and fixed are not usable. They are represented as Latin-1 characters (Avro's JSON form), not base64. Binary content cannot be passed through a mapping.
  6. Medium — maps with varying keys cannot be mapped. An import mapping only knows the keys from its sample JSON. The JSON itself is correct; handle it in a microflow or Java.
  7. Low — unknown fields are dropped silently when sending, and fields that are missing get their defaults. A typo in a field name therefore loses the value without an error when the field has a default.
  8. Medium — no schema registry client. The module does not fetch schemas or register them. On the consumer side the Get Avro Schema microflow plays the registry (cached per schema ID); on the producer side the Confluent Schema Id is entered by hand.
  9. Low — only the Confluent 4-byte format is recognised. Apicurio's 8-byte IDs, AWS Glue's UUID format and Avro single-object encoding are not supported. Schema IDs in Kafka headers can be read by the Get Avro Schema microflow (header parameters), but the cache is keyed by the payload's schema ID only.
  10. Low — keys are plain strings. Avro-encoded message keys are not decoded or encoded; headers are strings.
  11. Low — the Explorer decodes with the default schema only. The message explorer (GetMessagesFromOffset) honours the schema ID format but does not call the Get Avro Schema microflow.
  12. Low — schema changes need a restart. The consumer's default schema and the Get Avro Schema results are cached until the consumers restart; saving any Kafka setting restarts them on all nodes.
  13. Low — recursive schemas work in the module, but an import mapping only maps the depth present in its sample JSON.
  14. Medium — some enum symbols cannot be Mendix enumeration keys. Mendix reserves names such as NEW (CE7247). An Avro enum with such a symbol cannot be mapped one to one to a Mendix enumeration; map it to a String attribute, or rename the symbol in the schema.
  15. Medium — a wrapped optional needs a wrapper entity on export. An export mapping group writes {} when there is no object, which Avro rejects for a union (Expected start-union. Got END_OBJECT). Model the wrapper (e.g. {"shop.Address": {…}}) as an entity of its own and set the mapping to leave out empty elements; see 5.8.
  16. Low — the import mapping creates the wrapper object for null. For "priority": null the import creates the wrapper object without a value. Test the value, not whether the object exists.
  17. Low — timestamps cannot be converted in the mapping itself. Value converters for timestamp-millis failed to build in testing (CE0228/CE0230/CE5015). Map the number to a Long attribute and convert in a microflow (see 5.8).
  18. Low — a JSON sample with control characters (e.g. from a bytes field) could not be used to create a JSON structure in testing; another reason to avoid bytes fields.

5.7 Get Avro Schema microflow

A microflow with an Integer parameter SchemaId that returns the schema text, for example from an entity MyModule.AvroSchema (SchemaId, Definition) filled from your schema registry:

retrieve $Schema from MyModule.AvroSchema where SchemaId = $SchemaId (first)
return $Schema/Definition   -- empty → the consumer's default schema is used

Because the result is cached per schema ID per consumer thread, the microflow runs once per schema version per thread on each node, not once per message. It must therefore depend only on the schema ID.

5.8 End-to-end: an order through export mapping, Kafka and import mapping

The UnitTesting test Tests.TEST_AvroOrderEndToEnd runs an extensive order through the whole chain against a real broker, and compares what arrives with what was sent, field by field:

  1. SUB_CreateSampleOrder builds an order in memory: a full one (every optional filled, a note with non-ASCII characters, a description with quotes and €, two lines, two tags) and a minimal one (every optional empty, no tags).
  2. The export mapping EMM_AvroOrder turns each into JSON; SendSynchronousAvroWithSchema encodes it with the schema below and Confluent schema ID 43.
  3. The consumer (format Confluent) reads ID 43, gets the schema from the Get Avro Schema microflow Kafka_GetAvroSchemaForTest, decodes the message, and the listener stores the JSON.
  4. The import mapping IMM_AvroOrder turns the received JSON back into objects; SUB_CompareOrders compares them with the originals (lines matched by SKU, tags by value).

Both orders survive the round trip unchanged, including the timestamp to the millisecond, decimals, non-ASCII text and quotes. On export the mapping leaves out empty elements, and the module fills them in from the schema defaults (null, []), as the minimal order shows.

6. Recommendations for schema designers

  • Prefer required fields with defaults over ["null", X] unions, or use ["null","string"], which arrives unwrapped.
  • Expect dates and timestamps as numbers and plan a conversion step, or carry them as ISO strings in a string field if both sides agree.
  • Avoid bytes/fixed for anything the Mendix app has to read; use a base64 string field.
  • Avoid maps with dynamic keys; use an array of key/value records instead.
  • Use the Confluent format with a Get Avro Schema microflow that returns the exact schema per ID, so schema versions never get mixed up.
  • Keep decimal values within the declared precision and scale; the module will not warn.
