1. How it works

The module converts between Avro binary and JSON text. A Mendix developer never handles Avro objects: received messages arrive in the on-receive microflow as a JSON string, and messages are sent by passing a JSON string. Import and export mappings do the rest.

Receiving

  1. The consumer reads the message value as bytes: a consumer with an Avro configuration is switched to ByteArrayDeserializer when it is saved.
  2. The configuration's schema ID format decides how the bytes are split: Confluent expects byte 0, a 4-byte schema ID, then the Avro data; None treats the whole value as Avro data (no schema ID).
  3. The schema always comes from the configuration's Get Avro Schema microflow; there is no stored schema. The microflow gets the schema ID (empty when there is none) and can also take the topic, key, partition, offset, consumer and any header. Its result is cached per schema ID per consumer thread until the consumers restart; without a schema ID it runs for every message.
  4. That schema is the writer schema: the version the producer wrote with. If the configuration has a Get Reader Schema microflow, it is called with the writer schema's full name (RecordName, e.g. shop.Order) and returns the version your app expects (the reader schema), or empty. The two are checked for compatibility; the result is cached per writer schema and topic.
  5. The data is decoded with the writer schema and, if there is one, translated to the reader schema (Avro schema resolution: fields only the writer has are dropped, fields only the reader has get the reader's default, aliases match renamed fields). It is written as JSON. Decimals become plain numbers, and optional strings are unwrapped; everything else stays in Avro's JSON form (details in section 3).
  6. The JSON is passed as the Value (String) parameter of the on-receive microflow, with the record name (RecordName; for a union, the type of this message) and SchemaId if the microflow declares them, so a topic with several record types can be handled per type. Key and headers are passed as strings, as for non-Avro consumers.
  7. If any step fails (wrong format, schema microflow error, invalid schema, a writer schema that cannot be translated to the reader schema, data that does not match the schema), the message goes through the consumer's failure handling: Continue logs and skips it, Retry retries it until it succeeds.

Sending

  1. The microflow builds a JSON string (usually with an export mapping) and calls SendSynchronous or SendAsynchronous, optionally with a schema ID. The producer must have an Avro configuration.
  2. The schema comes from the configuration's Get Avro Schema microflow, called with the schema ID (empty when none is given), the topic, the key, the producer and any header; it is cached per schema ID on each node until the producers restart.
  3. The module fills in schema defaults for fields that are left out, converts decimals and optional strings to Avro's JSON form, and encodes the result with the schema.
  4. With schema ID format Confluent the schema ID is required, and byte 0 and the 4-byte ID are put in front of the data. With None the data is sent as is; the schema ID, if any, is only passed to the microflow.
  5. If the JSON does not fit the schema, the send action fails with an AvroTypeException in the calling microflow; nothing is sent.

General rules when sending (all verified):

  • A field that is left out gets its schema default: {"name":"Ada"} with defaults for country, score and note is written as {"name": "Ada", "country": "NL", "score": 0, "note": null}.
  • A required field without a default that is left out fails: AvroTypeException: Expected int. Got END_OBJECT.
  • Null for a required field fails: AvroTypeException: Expected string. Got VALUE_NULL.
  • A wrong type fails, e.g. "41" for an int: AvroTypeException: Expected int. Got VALUE_STRING. A number too large for an int fails as well.
  • Fields that are not in the schema are dropped silently: {"name":"Ada","nickname":"ada"} is written as {"name": "Ada"}.

4. Limitations

  1. Medium — schema evolution needs the writer schema per message and, for a stable shape, a reader schema. Avro data contains no field names. Decoded with a schema other than the one it was written with, the bytes are read against the wrong layout: a field added in the middle shifts the values without an error (5.6). So:
    • The Get Avro Schema microflow must return the exact schema for each schema ID (from your registry). With format Confluent that is always possible; with format None the message says nothing about its version, so the producer has to tell it otherwise (for example in a header the microflow reads).
    • To keep the JSON in the shape your import mapping expects while producers move on, add a Get Reader Schema microflow: every message is then translated to the reader version, and a version that cannot be translated fails with the reason (e.g. TYPE_MISMATCH at /fields/0/type: reader type: INT not compatible with writer type: STRING) instead of giving wrong data.
    • A writer schema that is a union of several record types is always decoded as written: its record name is only known per message. The on-receive microflow gets the type of each message as RecordName.
  2. Medium — optional fields other than strings are wrapped. ["null","int"], optional records, enums, arrays, timestamps and decimals arrive as {"int":41}, {"crm.Address":{…}} etc., and must be sent in that form (a plain value fails). Only ["null","string"] is unwrapped. In an import mapping each wrapper is an extra object level. Unions of several non-null types are always wrapped and have no single mappable shape.
  3. Medium — dates and times are numbers. date, time, timestamp-millis/micros and local-timestamp arrive as numbers (days, milliseconds or microseconds) and must be sent as numbers; an ISO date string fails. Convert them in a microflow. Studio Pro types these elements as Integer.
  4. Medium — decimal precision is not checked; values are rounded silently. A value with more decimals than the scale is rounded half-up (0.125 → 0.13 with scale 2). A value with more digits than the precision is written anyway (123456.78 with precision 4), which strict readers may reject. Decimals do arrive and can be sent with full precision (also as a JSON string for very large values).
  5. Medium — bytes and fixed are not usable. They are represented as Latin-1 characters (Avro's JSON form), not base64. Binary content cannot be passed through a mapping.
  6. Medium — maps with varying keys cannot be mapped. An import mapping only knows the keys from its sample JSON. The JSON itself is correct; handle it in a microflow or Java.
  7. Low — unknown fields are dropped silently when sending, and fields that are missing get their defaults. A typo in a field name therefore loses the value without an error when the field has a default.
  8. Medium — no schema registry client. The module does not fetch schemas or register them. The Avro configuration's Get Avro Schema microflow plays the registry on both sides (cached per schema ID); the schema ID to send is passed to the send action by the calling microflow.
  9. Medium — without a schema ID the microflow runs for every message. With format None (or a send without a schema ID) nothing can be cached by ID, so the Get Avro Schema microflow is called per message. Parsing is cached by schema text, but the microflow call itself costs time; keep it light (no database retrieve per message) or use the Confluent format.
  10. Low — only the Confluent 4-byte format is recognised. Apicurio's 8-byte IDs, AWS Glue's UUID format and Avro single-object encoding are not supported. A schema chosen by a Kafka header works with format None (the microflow gets the header as a parameter), but is then not cached.
  11. Low — keys are plain strings. Avro-encoded message keys are not decoded or encoded; headers are strings.
  12. Low — schema changes need a restart. The Get Avro Schema results are cached until the consumers and producers restart; saving any Kafka setting, including an Avro configuration, restarts them on all nodes.
  13. Low — recursive schemas work in the module, but an import mapping only maps the depth present in its sample JSON.
  14. Medium — some enum symbols cannot be Mendix enumeration keys. Mendix reserves names such as NEW (CE7247). An Avro enum with such a symbol cannot be mapped one to one to a Mendix enumeration; map it to a String attribute, or rename the symbol in the schema.
  15. Medium — a wrapped optional needs a wrapper entity on export. An export mapping group writes {} when there is no object, which Avro rejects for a union (Expected start-union. Got END_OBJECT). Model the wrapper (e.g. {"shop.Address": {…}}) as an entity of its own and set the mapping to leave out empty elements; see 5.8.
  16. Low — the import mapping creates the wrapper object for null. For "priority": null the import creates the wrapper object without a value. Test the value, not whether the object exists.
  17. Low — timestamps cannot be converted in the mapping itself. Value converters for timestamp-millis failed to build in testing (CE0228/CE0230/CE5015). Map the number to a Long attribute and convert in a microflow (see 5.8).
  18. Low — a JSON sample with control characters (e.g. from a bytes field) could not be used to create a JSON structure in testing; another reason to avoid bytes fields.

A Get Reader Schema microflow typically returns a constant per record type, the schema the import mapping was made from:

-- parameters: $RecordName (String)
if $RecordName = 'shop.Order' then return @MyModule.OrderReaderSchema
if $RecordName = 'shop.Customer' then return @MyModule.CustomerReaderSchema
return empty   -- other records: decode as written

On a topic with several record types, the on-receive microflow chooses the import mapping by $RecordName. The record name comes from the writer schema itself (its namespace and name), not from a header; the producer's subject naming strategy (TopicNameStrategy, RecordNameStrategy, TopicRecordNameStrategy) does not matter to the consumer, because schemas are fetched by ID.

5.7 Get Avro Schema microflow

A microflow with an Integer parameter SchemaId that returns the schema text, for example from an entity MyModule.AvroSchema (SchemaId, Definition) filled from your schema registry:

retrieve $Schema from MyModule.AvroSchema where SchemaId = $SchemaId (first)
return $Schema/Definition   -- empty fails the message (no default schema)

The same microflow serves receiving and sending. With a schema ID the result is cached (per consumer thread, and per Avro configuration for all sending threads of a node), so the microflow runs once per schema version, not once per message; for a given schema ID it must therefore always return the same schema.

Without a schema ID (format None, or a send without one) it runs for every message and decides itself, for example by a header:

-- parameters: $SchemaId (Integer), $MessageType (String, filled from the header MessageType)
if $SchemaId != empty then
  retrieve $Schema from MyModule.AvroSchema where SchemaId = $SchemaId (first)
else
  retrieve $Schema from MyModule.AvroSchema where MessageType = $MessageType (first)
return $Schema/Definition

Sending with format Confluent: SendSynchronous(producer, topic, key, value = $Json, …, schemaId = 42) calls the microflow with SchemaId 42 (once per node) and writes 42 in front of the message.

5.8 End-to-end: an order through export mapping, Kafka and import mapping

The UnitTesting test Tests.TEST_AvroOrderEndToEnd runs an extensive order through the whole chain against a real broker, and compares what arrives with what was sent, field by field:

  1. SUB_CreateSampleOrder builds an order in memory: a full one (every optional filled, a note with non-ASCII characters, a description with quotes and €, two lines, two tags) and a minimal one (every optional empty, no tags).
  2. The export mapping EMM_AvroOrder turns each into JSON; SendSynchronous (the saved test producer producer-avro with the Confluent test Avro configuration, schema ID 43) encodes it with the schema below and Confluent schema ID 43.
  3. The consumer (format Confluent) reads ID 43, gets the schema from the Get Avro Schema microflow Kafka_GetAvroSchemaForTest, decodes the message, and the listener stores the JSON.
  4. The import mapping IMM_AvroOrder turns the received JSON back into objects; SUB_CompareOrders compares them with the originals (lines matched by SKU, tags by value).

6. Recommendations for schema designers

  • Prefer required fields with defaults over ["null", X] unions, or use ["null","string"], which arrives unwrapped.
  • Expect dates and timestamps as numbers and plan a conversion step, or carry them as ISO strings in a string field if both sides agree.
  • Avoid bytes/fixed for anything the Mendix app has to read; use a base64 string field.
  • Avoid maps with dynamic keys; use an array of key/value records instead.
  • Use the Confluent format with a Get Avro Schema microflow that returns the exact schema per ID, so schema versions never get mixed up.
  • Give every new field a default and never change a field's type, so consumers with an older reader schema can keep translating new versions; rename with aliases rather than a plain rename.
  • Keep decimal values within the declared precision and scale; the module will not warn.
